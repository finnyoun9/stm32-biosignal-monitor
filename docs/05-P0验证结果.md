合计 **10 项，全部通过**。

### 单测抓到的真实 bug（值得写进调试记录）

- **现象**：读片内温度永远得到 `xx.00 °C`，小数部分恒为 0。
- **根因**：`TEMP_FRAC` 寄存器的小数部分在**高 4 位**（bit7:4），初版实现按低 4 位解析。
- **定位方式**：主机端单测里把 `TEMP_FRAC` 写成 `0x40`（期望 0.25 °C），实测输出 0 → 一次运行即定位。
- **修正**：`(frac >> 4) & 0x0F`。
- **意义**：这类 bug 在真机上要靠「一边加热探头一边读温度」才能发现，成本极高；解耦 + 模拟芯片把它变成毫秒级用例。

## 四、真实数据验证（PhysioNet BIDMC：同段 PPG 与 ECG 配对）

命令：

```bash
mkdir -p data/raw
# 逐条下载（PhysioNet 带宽有限，600 KB–1 MB/条，慢）
for r in bidmc01 bidmc02 bidmc03 bidmc04 bidmc05 bidmc06 bidmc07 bidmc08; do
  for e in hea dat; do curl -o data/raw/$r.$e https://physionet.org/files/bidmc/1.0.0/$r.$e; done
done
./.venv/bin/python tools/validate_bidmc.py --records bidmc01,bidmc02,bidmc03,bidmc04,bidmc05,bidmc06,bidmc07,bidmc08 --quiet --out data/validation_bidmc.csv
```

方法：30 s 滑窗；**用同一段记录的 ECG 心率作为独立真值**，对比 PPG 估出的心率。

| bidmc02 | 16 | 0.48 | 0.67 | 1.10 | 16/16 |
| bidmc03 | 13 | 2.49 | 5.78 | 11.20 | 13/13 |
| bidmc04 | 16 | 0.19 | 0.45 | 1.05 | 16/16 |

> 本表的结论不依赖具体条数：除 bidmc03 一例外，其余记录 MAE 都在 0.2 bpm 量级。

### 真实数据暴露的第二个 bug（比第一个更重要）

- **现象**：bidmc03 全部窗口的 PPG 心率都比 ECG 低约 **19 bpm**（PPG 76 vs ECG 95），而 PPG 自相关的主周期是 0.792 s → **75.8 bpm**，说明 PPG 是对的、**「真值」错了**。
- **定位**：打印 ECG 检测器的 R-R 间隔，发现规律是 `0.792 s, 0.160 s, 0.632 s, 0.168 s, …` —— 每个真实心搏后约 200 ms（正好等于不应期）就误报一个峰。再往下追，问题在**阈值**：初版只更新 SPKI（信号峰估计），NPKI（噪声峰估计）固定为前 2 秒的均值；该记录开头恰好安静，阈值因此长期偏低，积分信号一直高于阈值，于是「每过一个不应期就报一个峰」，心率被抬到 107 bpm。
- **修正**：按 Pan–Tompkins 原文做法，**SPKI 与 NPKI 都随局部极大值更新**（高于阈值者更新 SPKI，低于阈值者更新 NPKI）。
- **效果**：bidmc03 的 MAE 从 **19.33 → 2.49 bpm**；全量窗口 MAE 从 5.83 → **0.45 bpm**（8 例 125 窗口）；合成信号的 28 项单测仍全绿（无回归）。
- **遗留**：bidmc03 仍有 2 个窗口偏差较大（120 s 窗口 19.6 bpm）。逐窗看，PPG 始终稳定在 75.8，是**该窗口的 ECG 侧误检**（异位搏动/伪影）——即真值本身不可靠。这也是为什么验证脚本同时输出「逐窗表」而不是只给一个 MAE：**要能看到离群窗口，而不是被平均值掩盖**。

### 边界（必须主动说明）
- BIDMC 是 **ICU 静息数据**：受试者多卧床、心率范围集中、运动伪影少。它验证的是「采集链路 + 峰值检测算法」的正确性，**不等价于可穿戴在运动场景下的表现**。
- 这段验证用的是**数据集里的 PPG**，不是本项目硬件采的 PPG。真机数据的验证属于 P1（待上机）。
- 样本量如实标注：BIDMC 共 53 例，当前已验证 **8 例 125 窗口**（下载受 PhysioNet 带宽限制，脚本支持 `--records` 任意多条，仍在继续下载）。

## 四·补 C 固件侧算法与 Python 的一致性（P0 → P1 的关键衔接）

命令：`./.venv/bin/python tests/test_algo_conformance.py`

**为什么必须做**：P0 的结论（BIDMC 上 MAE 0.64 bpm）来自 **Python 实现**；上机跑的是 **C 实现**。
两者若不一致，那些数字对固件毫无意义。所以用同一批数据分别跑两边，把偏差量化出来。

| 数据 | C（固件，流式因果） | Python（离线，零相位） | 偏差 | 容差 |
|---|---:|---:|---:|---:|
| 合成 60 bpm | 60.0 | 60.0 | 0.0 | 3 |
| 合成 72 bpm | 72.3 | 72.3 | 0.0 | 3 |
| 合成 90 bpm | 89.5 | 89.6 | 0.1 | 3 |
| 合成 120 bpm | 120.0 | 120.0 | 0.0 | 3 |
| BIDMC 60 s 窗口 | 91.5 | 90.4 | 1.1 | 6 |
| BIDMC 180 s 窗口 | 89.8 | 90.4 | 0.6 | 6 |
| BIDMC 300 s 窗口 | 91.5 | 91.5 | 0.0 | 6 |
| BIDMC 420 s 窗口 | 90.9 | 90.4 | 0.5 | 6 |

**两侧的已知差异（是约束，不是 bug）**：
- Python 用 `filtfilt`（零相位，需要未来数据）；MCU 只能**因果**滤波，因此 C 侧用双二阶级联并接受固定群延迟；
- 质量指标：Python 用逐搏模板相关性；C 侧改用 RR 稳定性 + PI（MCU 上算相关性代价过高）。

**顺带修掉的一个隐患**：C 侧初版把 75–130 Hz 全部套用 100 Hz 的滤波系数，等于**静默算错**
（症状是「波形有点怪但心率还能出」，真机上极难发现）。现已改为：只支持 50/100/125/200 Hz（±10%），
其余采样率**明确失败**并置 `ready=false`，同时补上 125 Hz 系数（BIDMC 与不少可穿戴都用 125 Hz）。

## 四·补二 低功耗预算（P2 的前置件）

命令：`./.venv/bin/python tests/test_power_budget.py`

P2 的功耗目标是可计算的，不必等上机：`firmware/app/power_budget.c` 与 `tools/power_budget.py` 是同一套整数公式的两侧实现。

| 验证 | 结果 |
|---|---|
| C 与 Python 逐例一致 | **7 例配置全部一致**（平均电流 / 占空比 / 续航 / 反解值） |
| 手算期望值对照 | 4 例关键配置与手算数字一致（如 1 分钟一次 → 887 µA、200 mAh → 225 h） |
| 反解（给定目标求最长活动时间） | 1 分钟周期、目标 500 µA → **最多醒 896 ms**；目标 10 µA（低于睡眠 22 µA）→ **判不可达** |
| 非法配置 | 周期为 0 / 活动 > 周期 / 采样 > 活动 三种情况均被拒绝并给出错误码 |

结论表见 `docs/06-P2低功耗设计.md`（连续模式 22 mA 仅 9 h vs 1 分钟一次 887 µA 约 9.4 天）。

**两侧差异（如实说明）**：C 侧为实时性只做**因果**滤波，且**没有实现 RR 回检**（Python 有）；
因此在伪影/异位搏动处 C 可能漏检，容差相应放宽到 8 bpm。另外 C 侧检出的心搏数比 Python 多 2–3 个
（边界处的处理不同），而心率取 RR 中位数，所以不影响结果。
